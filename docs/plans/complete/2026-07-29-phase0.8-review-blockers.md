## A deliberate change in how this plan is written

The previous three plans prescribed exact test code. Implementers found **eleven** defects in it: tests routed through short-circuiting functions, an arithmetically impossible timeout, a fixture that resynced the very state under test, a proof mutation that was behaviour-preserving in Go, and a test that never reached the branch it named. The review then found that several `-run` filters in those plans **matched no test at all** — and `go test -run` with zero matches prints `ok` and exits 0, so those proof steps silently verified nothing.

So this plan states **invariants and concrete failure scenarios**. It does not prescribe test bodies. Each task requires the implementer to:

1. Design the test itself, against the stated invariant.
2. Prove it fails when the invariant is broken, and **paste the output showing the test actually ran** — a `-run` filter that selects nothing is a failed proof, not a pass. Always confirm with `-v` and check for `=== RUN`.
3. State in its report what it would take for the test to pass against a broken implementation, and why that cannot happen.

### Task H1: Make `netConn` writes safe (Criticals C1 + C2)

**Files:** `internal/server/server.go`, `internal/server/deliver_internal_test.go`

Two defects, one root area, fix together.

**C1 — the deadline is never cleared, and it kills `fundi attach`.**
`Deliver` sets a 5s write deadline on the **connection**; nothing resets it (`grep SetWriteDeadline` → one hit). `handleConn`'s response write sets none of its own, so it fires against the *expired* deadline, returns `i/o timeout`, and `handleConn` returns — closing the socket.

`attach` issues `ctrl_subscribe` **and** every later request (prompt, abort, steer) on **one** socket. Reproduced on the real server: subscribe → receive an event → wait 6s → send a request → `i/o timeout` → EOF. **So attach dies on the first prompt sent more than 5s after the last event** — every normal pause for reading. `fundi-helpers/index.ts` has the same shape.

**C2 — a concurrent `Deliver` postpones a blocked write indefinitely, and frames can splice.**
Go documents `SetWriteDeadline` as applying to "all future **and pending**" writes. `netConn` is written concurrently from `DeliverToChild`, `DeliverToGlobal`, `DeliverToMatching` and `Server.Broadcast` on separate goroutines, with **no mutex**. So a peer `Deliver` resets the deadline to `now+5s` and a write blocked on a non-draining subscriber never expires — reproduced: a blocked write with a 300ms deadline survived >3s under a 100ms reset ticker. Streaming's ~4 frames/sec/child makes those resets continuous, so **the Critical D4 was written to fix is still reachable.**

The same missing mutex means `WriteFrame`'s two writes (payload, then `\n`) can interleave between goroutines, splicing frames. JSONL only resyncs by discarding both.

**Invariants to establish:**
1. A write deadline set for one write must not affect any later write on that connection.
2. Concurrent writers on one connection must not extend each other's deadlines.
3. Two concurrent frame writes must never interleave — every frame on the wire is contiguous and parseable.
4. A blocked write must still time out within its own budget regardless of peer activity, and must log at `warn`.
5. A response write from `handleConn` must not inherit or be broken by a subscription write's deadline.

**Direction, not prescription:** clear the deadline after each write *and* serialize writes per connection. Routing `handleConn`'s response through the same `netConn` is the obvious way to get both properties in one place — but check whether `handleConn` has a `netConn` to hand at that point, and say what you find. Preserve G1's severity classification (`isRoutineConnClose` → debug, everything else warn) exactly.

**Do not** solve C2 by removing the deadline; it exists because a blocked write wedges `monitorChild`, which also drives status transitions, rename detection, session-id sync and child-exit handling.

**Testing note:** the existing test uses a single `net.Pipe` and a single `Deliver`, which is structurally incapable of seeing either defect. Your tests must involve a second write and a second goroutine. Run them under `-race`.

### Task H2: Revert G2; fix the race where it actually lives (Critical C3)

**Files:** rafiki — `store/lock.go`, `llm/conversation.go`, `agentloop/agentloop.go`, `agentloop/agentloop_test.go`. fundi — `internal/agent/orphans.go` and its tests.

**C3 — the lock deadlocks, in a function nothing calls.**
`store.LockConversation` pins a `*pgxpool.Conn` for the lock's lifetime, and `fabricateOrphanResults` then makes further **independent pool calls** (`conv.History` → `Messages.Load` → `m.pool.Query`; `conv.AppendUser`). So each in-flight Resume needs **two** simultaneous connections. `pgxpool` defaults `MaxConns` to `max(4, NumCPU)` and `cmd/rafiki/main.go` uses bare `pgxpool.New`. Reproduced with `MaxConns=2` and **two different** conversations — no lock contention whatsoever — as `load messages: context deadline exceeded`, and an unbounded hang without a deadline.

**And the target was dormant.** `agentloop.Resume` has **zero non-test callers in either repo**. fundi's actual orphan-fabrication path is `internal/agent/orphans.go`'s `RepairOrphans`, called at every child boot and on the abort path — and it performs the same unlocked read-then-write. So G2 hardened dead code and introduced a deadlock into it, while the live path stayed racy.

**Do this:**
1. **Revert G2** (`3c54ad7`) in rafiki — the lock, its `llm` accessor, and the `agentloop` wiring. Restore the pre-G2 comment, then **correct** it: it must not re-assert "naturally once-per-id", which is false. State plainly that fabrication is not concurrency-safe and why that is currently acceptable (no caller).
2. Keep `TestConcurrentResume`, but mark clearly that it documents a **known unfixed** race in a function with no production callers. Do not delete it — it is the record. If it must be skipped to keep CI green, `t.Skip` with the reason, not a deletion.
3. **Assess `RepairOrphans` in fundi** and report before changing it: is concurrent invocation actually reachable? The review notes fundi's agent refs default to the unique `FUNDI_CHILD_ID` and `Controller.Resume` requires `StatusExited`, so it may not be. **If it is not reachable, do not add locking** — document the invariant that makes it safe and stop. Adding a lock to a second unreachable path would repeat G2's mistake.

**If you conclude the race is reachable in `RepairOrphans`, STOP and return NEEDS_CONTEXT with your evidence** — the fix choice (advisory lock scoped to avoid pinning, conditional insert, or a unique-constraint migration) is the user's call, not yours.

**Verification:** rafiki full suite 0 with 0 skips; `go test ./agentloop/ -run TestConcurrentResume -count=10` behaving as documented (skipped, or failing as a known race — state which); fundi build and tests unaffected.

### Task H4: Stop `paths.base()` failing silently (Important I10)

**Files:** `internal/paths/paths.go`, `internal/paths/paths_test.go`

When `os.UserHomeDir()` fails, `base()` returns a **relative** path. Two warnings that would have surfaced this were removed by earlier tasks (`d882c12` dropped the CLAUDE.md warn, `8fdf700` the skills-dir warn) and neither was replaced. This violates the project's "never silently swallow errors" rule outright.

Concretely: the daemon's `SocketPath()` becomes `.local/state/fundi/controller.sock` relative to *its* cwd, `MkdirAll` succeeds, and a CLI run from any other directory reports "daemon isn't running" against a healthy daemon. For children, `.config/fundi/instructions.md` relative to the *project* cwd means a repo that happens to contain that file gets it silently promoted to user-global instructions.

**Invariant:** a failed home-directory resolution is observable in the logs, and remains observable on repeated calls (`base()` is called once per path resolution, so a naive log would spam).

**Direction:** a `sync.Once`-guarded warn is the obvious shape, but note the review's caveat — once *per process* is right; once for all time across a long-lived daemon may hide a later occurrence. Decide and justify. No test currently leaves `HOME` unset; yours should.

### Task H6: Don't unmarshal partial tool_use input (Important I2, fresh regression)

**Files:** `internal/agent/emit.go`, `internal/agent/emit_test.go`

Introduced by `d53d5dc` (Phase 0.6). `MapAssistantMessage` now reads `b.Input` directly and `json.Unmarshal`s it. But per the SDK, the first `InputJSONDelta` **replaces** `{}` with a partial fragment and later ones append — so mid-stream `b.Input` is a JSON *prefix* like `{"file_path": "/Users/b`.

`hasContent` returns true for `b.Type == "tool_use"` regardless of input, so the block flushes immediately (valid `{}`) and every later flush lands mid-fragment: roughly 4 `slog.Warn`/sec **plus garbage `{"_raw": …}` in `message_update`**, for any tool call whose input takes >250ms to stream — i.e. essentially every `Write` or `Edit`.

The old `AsAny()` path returned `input:{}` — wrong, but benign.

**Invariant:** a `message_update` never carries a tool_use block whose arguments are a truncated JSON fragment, and no warning is logged for input that is merely still streaming. A genuinely malformed *complete* input must still warn and still fall back to `{"_raw": …}`.

The existing guard is vacuous: it accumulates a single **complete** fragment, so it never sees a prefix. Your test must accumulate a partial one.
